# Как участвовать в разработке

Спасибо, что хотите помочь Breeze. Здесь описано, как предложить изменение, как устроены версии и выпуски и каким
правилам следует код. Как собрать проект и запустить тесты — в [README](README.md#для-разработчиков).

## Порядок работы

1. **Задача.** Для заметного изменения сначала создайте задачу или найдите готовую и договоритесь о подходе. Мелкие
   исправления можно присылать сразу.
2. **Ветка** от `main`: `feature/<кратко>` для новой функции, `fix/<кратко>` для исправления, `docs/<кратко>` для
   документации. Прямо в `main` не коммитят.
3. **Коммиты** короткие и законченные. Сообщение — на русском, в повелительном или описательном виде: «Поиск
   учитывает files.exclude», «Исправлено зависание при закрытии вкладки».
4. **Проверка перед PR:**
   - сборка проходит без предупреждений: `dotnet build CodeEditor.slnx`;
   - тесты зелёные: `pwsh ./build/test.ps1`;
   - если менялся интерфейс — UI-тесты зелёные: `pwsh ./build/test.ps1 -Ui`;
   - если менялся горячий путь — запущен его бенчмарк, результат сравнён с прошлым замером.
5. **Pull request** в `main`. Опишите, что и зачем изменено и как проверено. Если изменение видно пользователю,
   добавьте строку в раздел «Не выпущено» файла [CHANGELOG.md](CHANGELOG.md).
6. **CI** (`.github/workflows/ci.yml`) собирает Release и запускает все тесты, кроме UI. PR вливается, когда CI зелёный.
   Вливание — squash: одна задача — один коммит в `main`.

Значимое решение — новая зависимость, формат данных, архитектурное правило — опишите в задаче или PR: контекст,
решение, последствия.

## Версии

Версии следуют [SemVer](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH[-pre-release]`.

| Часть | Когда растёт |
| --- | --- |
| `MAJOR` | несовместимые изменения настроек, данных или поведения. До 1.0 не меняется: версии `0.x` ещё нестабильны |
| `MINOR` | новые возможности |
| `PATCH` | только исправления |
| `-alpha.N` | ранние версии: функции ещё появляются и меняются |
| `-beta.N` | функции готовы, идёт стабилизация |
| `-rc.N` | кандидат в выпуск |

Путь к первой стабильной версии: `0.1.0-alpha.1` → `0.1.0-alpha.2` → … → `0.1.0-beta.1` → `0.1.0-rc.1` → `0.1.0`.

**Откуда берётся версия.** В `Directory.Build.props` задана версия локальной сборки — `0.1.0-dev`. Выпуск получает
номер из git-тега: тег `v0.1.0-alpha.2` превращается в `-p:Version=0.1.0-alpha.2`. SDK дописывает к версии коммит,
поэтому «Справка → О программе» показывает, из какого коммита собрана программа. Версию в файлах перед выпуском
менять не нужно, достаточно тега.

## Выпуск новой версии

1. Убедитесь, что `main` зелёный в CI, а UI-тесты локально проходят: `pwsh ./build/test.ps1 -Ui`.
2. В [CHANGELOG.md](CHANGELOG.md) переименуйте раздел «Не выпущено» в версию с датой, например
   `## [0.1.0-alpha.2] — 2026-10-20`. Над ним добавьте пустой «Не выпущено», а внизу — ссылки на сравнение версий.
   Текст раздела станет заметками к выпуску, поэтому пишите его для пользователя.
3. Закоммитьте изменения: «Выпуск 0.1.0-alpha.2».
4. Поставьте тег и отправьте его:

   ```bash
   git tag v0.1.0-alpha.2
   ```

   ```bash
   git push origin main v0.1.0-alpha.2
   ```

5. Тег запускает [release.yml](.github/workflows/release.yml). Workflow:
   - проверяет, что в CHANGELOG есть раздел версии;
   - собирает и тестирует проект;
   - публикует самодостаточную сборку `win-x64` и собирает пакеты Velopack с дельтой от прошлого выпуска;
   - создаёт выпуск на GitHub с `Setup.exe`, переносным zip и пакетами обновления;
   - добавляет аттестацию происхождения.

   Если в версии есть `-`, выпуск помечается как предварительный.
6. Проверьте выпуск: скачайте `Setup.exe`, установите и посмотрите версию в «Справка → О программе». Установленная
   прошлая версия должна найти обновление через «Справка → Проверить обновления…».

Если выпуск не удался, исправьте причину, удалите тег и поставьте его заново:

```bash
git push origin :refs/tags/v0.1.0-alpha.2
```

Опубликованный выпуск не переписывают: если ошибка уже ушла к пользователям, выпустите следующую версию.

## Правила кода

Эти правила проверяют компилятор, анализаторы и архитектурные тесты (`tests/CodeEditor.Architecture.Tests`). Если
архитектурный тест падает, исправляют код, а не тест.

### Архитектура

- Слои: `Core` → `Shell` → `UI` / `Shell.Wpf` → `App`.
- Модули: `CodeEditor.Modules.X` (логика) + `CodeEditor.Modules.X.Wpf` (представления) + при необходимости
  `CodeEditor.Modules.X.Contracts`.
- Новый модуль добавляется в `AppHost.Modules()` и в `Layers` архитектурных тестов и получает свой проект `*.Tests`.
- Логика и ViewModel живут в сборках `net10.0` без WPF. WPF разрешён только в `CodeEditor.UI`, сборках `*.Wpf` и
  `CodeEditor.App`.
- Модуль не ссылается на реализацию другого модуля, только на его `*.Contracts`.
- Панели регистрируются через `IToolWindowRegistry`, представления — через `IViewRegistry`, команды — через
  `ICommandRegistry`, пункты меню — через `IMenuRegistry`. Оболочку ради модуля не меняют.
- Любое действие — команда с id. Меню, сочетания клавиш, палитра и инструменты агента строятся из команд.
- Документ (`IDocument`) отделён от представления. ViewModel не знает о типах AvalonEdit.

### Код

- Понятные имена, короткие методы, ранний выход вместо вложенности. Без магических чисел, дублирования и
  закомментированного кода.
- Одна ответственность на класс. Класс — до ~300 строк, метод — до ~40.
- Один публичный тип на файл, имя файла совпадает с именем типа. Папки внутри модуля: `Commands/`, `Services/`,
  `ViewModels/`, `Views/`.
- Зависимости приходят только через конструктор. Без service locator и статических синглтонов. Классы `sealed` по
  умолчанию.
- Подходящие структуры данных: `FrozenDictionary` для справочников, `ImmutableArray` для снимков, `Channel<T>` для
  потоков. Регулярные выражения — через `[GeneratedRegex]`, журнал — через `[LoggerMessage]`.
- На горячих путях нет O(n²) и повторных проходов. Сложный оптимизированный код пишут только там, где замер показал
  узкое место.
- Комментарии, XML-doc, тексты журнала и исключений о программных ошибках — на английском. Тексты для пользователя
  и модели — только в `Resources/Strings.resx` (английский) и `Strings.ru.resx` (русский).
- Nullable включён, предупреждения считаются ошибками, анализаторы .NET включены.

### Интерфейс

- Ориентиры — VS Code, Visual Studio и Rider: берём полезное, но без перегрузки. Редкое — в меню и палитре, а не на
  экране.
- Клавиатура и мышь на равных: у любой команды есть сочетание или пункт палитры и пункт меню либо видимый элемент.
- Только `DynamicResource` и токены темы из `CodeEditor.UI`, никаких цветов в разметке. Отступы 4/8/12/16, шрифты
  Inter и Cascadia Mono, анимации не длиннее 150 мс.
- У каждого интерактивного элемента задан `AutomationProperties.AutomationId`: на него опираются UI-тесты.
- Code-behind содержит только визуальную логику.

### Производительность

| Метрика | Бюджет |
| --- | --- |
| Холодный старт до окна с папкой | ≤ 1 с (Release) |
| Память в простое, папка на 10 000 файлов | ≤ 150 МБ |
| Задержка ввода символа | ≤ 16 мс |
| Открытие файла 10 МБ | ≤ 300 мс, UI не блокируется |
| Поиск по 10 000 файлов | первые результаты ≤ 200 мс, дальше потоком |
| 100 раз открыть и закрыть вкладку | память возвращается к исходной |

- Модули и панели активируются лениво. UI-поток только рисует: файлы, поиск и анализ работают в фоне с
  `CancellationToken`.
- Списки и деревья виртуализированы. Панели и документы реализуют `IDisposable` и отписываются от событий.
- Каждый новый NuGet-пакет оценивают по размеру и влиянию на старт.

### Тесты

- Новая логика покрывается модульными тестами xUnit в соответствующем `*.Tests`.
- Сквозные сценарии проверяют UI-тесты (FlaUI) через `AutomationId`.
- Горячие пути получают бенчмарк в `CodeEditor.Benchmarks` с `[MemoryDiagnoser]`.
